# core

Calx: the apps' core, built with the server as one static library that the desktop and iPhone apps link. It keeps the WebSocket to the instance, logs in, keeps the SQLite cache and the outbox, and catches up through the event log.

Only JSON crosses its C boundary:

```c
uint8_t *loom_core_start(const uint8_t *config_json, size_t len, loom_event_fn on_event, uint8_t *ctx);
void      loom_core_send(uint8_t *core, const uint8_t *json, size_t len);
void      loom_core_stop(uint8_t *core);
bool      loom_push_open(const uint8_t *keyring, size_t klen, const uint8_t *sealed, size_t slen, loom_event_fn on_text, uint8_t *ctx);
```

`loom_push_open` is for the iPhone's notification service extension, which runs without a core. It opens a notification that came [through the push relay](../protocol/protocol.md#through-the-push-relay): it takes the notification's `sealed` and the keyring service the core was started with, and hands `on_text` the notification as the instance made it. When it doesn't open, it gives false.

## Files

- [`lib.calx`](lib.calx): the C boundary. `calx build --staticlib core/lib.calx` makes the library and `loomcore.h`. `loom_core_start` runs the connection on a thread of its own, and a second thread hands what it says to `on_event`. It returns at once: an instance in the app starts on the connection's thread before it connects, so the app draws its window from the cache meanwhile. `loom_core_stop` waits for both threads and the instance, so no `on_event` comes after it returns.
- [`conn.calx`](conn.calx): the connection to the instance (LOO-22). It opens one WebSocket to `/ws`, says `hello` with its cursor, then forwards catch-up and live frames to the app. When the connection ends, it opens again after 0.5 s, doubling up to 30 s, plus up to 20% at random. It opens again at once on wake or a network change. It stops for good on 4001 (signed out) and 4002 (update needed). It follows a moved instance: it keeps the instance's key from the first `welcome`, checks a `moved` frame's signature with it, asks the new place's `/api/info` for its key (again every 2 s until it answers), and only when the keys match moves the token in the credential store to the new address and connects there with the same cursor.
- [`update.calx`](update.calx): the app's own updates, looked for on a timer while it runs and checked against the release key ("Config", below).
- [`updates.calx`](updates.calx): what's behind across the app, in the first core: the app and each server, who may update what, and what updating everything does, servers first and the app last (LOO-159).
- [`login.calx`](login.calx): login, setup and logout over the instance's HTTP API (LOO-23). The core's loop starts each request and checks it on every turn, so nothing waits while the instance hashes a password. The device token is kept in the system's credential store with std.keyring (Credential Manager, the Keychain), under the service `loom` and the instance's address. A 4001 close forgets it.
- [`device.calx`](device.calx): this device as a tool for agents (LOO-37, LOO-39: screenshots and the clipboard, which it asks the app for). Its Ed25519 key and the person's choice for each tool (off, ask or allow) are kept in the cache. It tells the instance both on welcome, signs the approvals given here, and acts on a `device.call` only as the person chose here, and for a tool that asks, only with this device's own signature of the exact request. Commands run in PowerShell or zsh without holding up the loop. It keeps the person's hosts too, each with its own off, ask or allow, and runs their commands through `ssh`. A host also takes `install_loom`, a plan the person signed here, which always needs that signature.
- [`install.calx`](install.calx): loom going onto one of the person's hosts, for an agent's `install_server` (LOO-167, protocol.md, "Installing loom on a host"): the commands made from the signed plan, run over ssh one after another, `device.progress` for each step, `core.offer` to this app with the link code, which stays here, and `/api/version` on the new server until it's set up.
- [`hosts.calx`](hosts.calx): the person's own servers as devices (LOO-165, PLAN.md, "Your hosts"): reading the hosts in `~/.ssh/config` and the machines in `tailscale status --json`, and the `ssh` command that runs one command on a host, with `BatchMode` and the command after `--`. [`shared/hosts.calx`](../shared/hosts.calx) checks a name or target, which the instance checks too.
- [`relay.calx`](relay.calx): reaching an instance in a desktop app over Noise ([protocol.md, "Over Noise"](../protocol/protocol.md#over-noise)), as a phone does. Such a place is `noise://<the instance's Noise key, hex>@192.168.1.20:47420,100.101.1.2:47420`, its addresses in the order to try them. The relay listens on 127.0.0.1 on a thread of its own, and the rest of the core uses it as any instance: each `/ws` there becomes a Noise socket to the PC, and its HTTP requests go through one more. An address that doesn't answer in 5 s gives way to the next. The token is kept under `noise://<key>`, so a PC found at new addresses keeps it. When none of a place's addresses answer, the relay looks for the instance by its key with mDNS (`look_up`, at most every 30 seconds) and tries the addresses it says it's at, the home network's first. On the PC, `own_addresses` gives what goes in the QR code while phones are on: the IPv4 addresses of the interfaces that are up, the local network's first and Tailscale's next, from `std.net.interfaces`, leaving out loopback and the networks inside the machine (Hyper-V, WSL, Docker, Podman, libvirt).
- [`pushbox.calx`](pushbox.calx): the phone's side of the push relay (LOO-64): its box key, kept in the credential store as `push box`, `push.register` with the APNs token sealed for the relay, which `conn.calx` sends whenever `welcome` has a `relay`, and opening a sealed notification for `loom_push_open`.
- [`cache.calx`](cache.calx): the local SQLite cache (LOO-24), `core.db` in the app's data folder: agents, conversations, messages, devices, the runs still going, their tool calls and the questions still open. Each event is applied in one transaction with the cursor, its `seq`, and before the app hears of it, so the two never drift apart. A snapshot after `reset: true` replaces it all, and a login as someone else, or to another instance, clears it. The outbox is here too: a `send` waits with its client id until the instance acks it, and goes again on each reconnect.

## Config

`loom_core_start` takes `{"server": "https://loom.example.com", "data": "C:\Users\…\AppData\Roaming\Loom"}`, both optional. `server` may be a `noise://` place too ([`relay.calx`](relay.calx)). `data` is the folder for the cache, which is kept in memory without one. With `server`, or the one the cache last knew, the core looks for a token kept for it and connects; without a token, it waits for a login. With `tz`, the system's time zone as an IANA name (the desktop app reads it with `iana-time-zone`), the core gives it to the instance in `hello` and in a login's `device`, so routines at a time of day keep the person's clock. Tests also give `token`, and `keyring`, a service of their own.

With `"mode": "local"` the core first starts an instance of its own ([PLAN.md, "An instance in the desktop app"](../PLAN.md#an-instance-in-the-desktop-app)): the server code, on a thread, listening on 127.0.0.1 on the port it had last time (`{data}/instance/port`), or a free one if that's taken, with its data in `{data}/instance`. It finds the ACP agents installed on the computer, makes a device for "This computer" owned by `username` (default `me`) of kind `kind` (default `windows`), and connects with that device's token, which is new every launch. Its cache is `{data}/local.db`, apart from `core.db`, so an instance elsewhere keeps its own. `loom_core_stop` stops the instance too.

With `"version": "0.3.0"`, the core keeps the app up to date (PLAN.md, "Updates and versions"). A little after it starts, then about every ten minutes while it runs (10 minutes, give or take 1, so every app doesn't ask at once), it reads the newest release's `manifest.json` and `manifest.json.sig` from `update` (GitHub's latest release, unless the config names another manifest; an empty `update` turns it off). If the signature is the release key's (`shared/release.calx`) and the release is newer, it downloads the file for `platform` (default `windows-desktop`; the Windows app asks for `windows-installer`, the release's `loom-setup.exe`) into `{data}/update/<version>/`, checks its SHA-256 against the manifest, and tells the app `core.update`. The app hands it to that setup, which swaps it in (desktop/setup). Builds from source leave `version` out. With `update_key`, a public key in hex, releases are checked against it instead of the release key: a build from source trying a test's releases. Each manifest it checks, newer or not, also tells the app `core.release`, and the core compares it with its instance's version (`core.server`). A look the timer starts asks with the last manifest's ETag (`If-None-Match`), and a 304, or a manifest with the same bytes as the last one whose look ended well, is nothing new: no signature is read and nothing is said. A look the app asks for (`update.check`) always reads the manifest whole.

With `"hub": true`, which the app gives its first core, the core gathers what's behind across the app for the update icon (`core/updates.calx`): the app's own update from its updater, its own instance, and each other server's `core.server`, which the app hands it as `server.state`. It says `core.updates` whenever that changes, and `updates.run` updates one device or everything: servers through `core.relay`, and the app last, with `core.restart`.

## Between the app and the core

The app sends the core protocol frames (`send`, `cmd`, `approve`, `cancel`, …), which go on to the instance as they are, and these of the core's own:

| From the app | Means |
|---|---|
| `{"t":"login","id":"l_1","server":"https://…","username":"…","password":"…","device":{"name":"Desk PC","kind":"windows","tz":"Europe/Oslo"}}` | Logs in (`POST /api/login`). `server` may be left out once one is known |
| `{"t":"setup", …, "code":"…"}` | Sets a new instance up (`POST /api/setup`), with the code it printed |
| `{"t":"link","id":"l_2","qr":"loom://link?…","device":{…}}` | Joins the instance in a QR code another device shows (`POST /api/link`), as a login does. `core.login` answers, with `bad_qr` for text that isn't loom's |
| `{"t":"link","id":"l_5","server":"https://…","code":"loom-link-…","username":"elliot","device":{…}}` | Signs in with a [link code](../protocol/protocol.md#link-codes) from `core.offer` (`POST /api/link`), as a login does: on a new server it makes the owner, as `username`. `core.login` answers, with `bad_server` for an address that isn't one |
| `{"t":"invite.join","id":"l_3","link":"https://loom.example.com/join/<code>","username":"…","password":"…","device":{…}}` | Makes an account from an invite link (`POST /api/join/<code>`), with the username and password the person picked, and logs in, as a login does. `core.login` answers, with `bad_link` for text that isn't an invite link |
| `{"t":"reset.use","id":"l_4","link":"https://loom.example.com/reset/<code>","password":"…","device":{…}}` | Sets a new password with a reset link (`POST /api/reset/<code>`) and logs in with it. `core.login` answers, with `bad_link` for text that isn't a reset link |
| `{"t":"logout"}` | Revokes this device's token (`POST /api/logout`), forgets it, and signs out |
| `{"t":"send","conversation":"c_9","text":"…"}` | A message the person wrote. It goes in the outbox, with a `cid` if it has none, and out when the connection is up. With `agent` instead of `conversation`, it goes to that agent's newest conversation, which the core makes first if there's none: the desktop app shows each agent as one ongoing chat |
| `{"t":"core.get","id":"g_1","what":"messages","conversation":"c_9","before":"msg_40","limit":50}` | Reads the cache: `what` is `conversations`, `agents`, `devices`, `runs`, `tools`, `approvals`, `outbox` or `messages`. Older messages than the cache has come from the `messages.list` command, whose result the cache keeps |
| `{"t":"app.active","active":false}` | Someone started or stopped looking at the app. The core notifies only while no one is, and tells the instance (the `device` frame) |
| `{"t":"app.wake"}` | The system woke from sleep. The core opens a new connection at once |
| `{"t":"app.network"}` | The network changed. The same |
| `{"t":"file.upload","id":"u_1","path":"C:\\Users\\…\\shot.png"}` | Sends a file to the instance (`POST /files`), up to 64 MB. `core.file` answers with its `file`, which goes in a `send`'s `files` |
| `{"t":"file.get","id":"f_1","file":"9f86d0…","thumb":true}` | Fetches a file, or with `thumb` its thumbnail, into `{data}/files/`, and `core.file` says where. A file goes in a folder of its own, under its `name` if one is given, so the program that opens it knows its kind. One it has already is answered at once |
| `{"t":"device.answer","call":"tc_5","ok":true,"output":"…","image":"/9j/4AAQ…","mime":"image/jpeg"}` | The app did what `core.device_ask` asked. The core sends it on to the instance as `device.result`, only for a call it asked |
| `{"t":"hosts.scan"}` | Finds the person's hosts: the `Host` names in `~/.ssh/config`, but patterns, and the machines `tailscale status --json` names, but phones. `core.hosts_found` answers, without the ones added already |
| `{"t":"host.add","target":"root@vps","via":"ssh"}` | Adds a host by what ssh is given, asking before each command from the start. Its name is the target without the user. `core.device` answers, or `error` with code `host` for a target that isn't a host, or a name taken |
| `{"t":"host.set","name":"vps","mode":"allow"}`, `{"t":"host.remove","name":"vps"}` | Sets what agents may do on a host, `off`, `ask` or `allow`, or takes it away. `core.device` answers, and the instance hears the hosts as they are now |
| `{"t":"update.check","id":"u_2"}` | Looks for an update now. `core.update` answers, with the id |
| `{"t":"release","version":"0.2.1"}` | The newest release, as the core that looks for app updates found it (`core.release`). The app hands it to each of its servers' cores, which says `core.server` |
| `{"t":"server.update","now":false}` | Has this core's instance update itself: the core sends `instance.update` (`now` stops what runs) and says how it goes in `core.server`'s `update`. One that isn't connected is `failed`, saying so |
| `{"t":"server.state","dir":"servers/2","loom":"0.2.0","latest":"0.2.1","behind":true,"may":true,"can":true}` | To the first core: another server's `core.server`, as the app had it from that server's core, with the server's folder in the app as `dir`. `"gone":true` when the app forgets the server |
| `{"t":"updates.run","device":"servers/2"}` | To the first core: update one device, `"app"` or a server's folder, or with no `device`, everything behind this person may update. What it does comes back as `core.relay` and `core.restart` |
| `{"t":"core.stop"}` | Sent by `loom_core_stop`. The core closes the connection and ends |

The core tells the app every frame the instance sends (`welcome`, `event`, `delta`, `synced`, `ack`, `result`, `error`, …), after the cache has taken it. Events it has applied already aren't sent again. The `result` of a `link.create` the app sent gets `qr` in its `value`: the text the app draws as the QR code, `loom://link?a=<address>&c=<code>&i=<instance>&k=<key>` ([`link.calx`](link.calx)), with the address this core reaches the instance at, which may be a `noise://` place. The `result` of an `invite.create` gets `link`, `<the instance's address>/join/<code>`, and of a `password.reset`, `<the instance's address>/reset/<code>`, to pass on, for an instance at an `http://` or `https://` address. Deltas go on only when they add text: a repeat is dropped, and a gap means one was lost, so the core reconnects and gets the reply again from position 0. And these of its own:

| From the core | Means |
|---|---|
| `{"t":"core.conn","state":"connecting"}` | Opening the socket, or `hello` is sent and `welcome` hasn't come |
| `{"t":"core.conn","state":"live"}` | Welcomed. Catch-up follows, then `synced` |
| `{"t":"core.conn","state":"offline","retry_ms":540,"why":"…"}` | The connection ended. It tries again after `retry_ms` |
| `{"t":"core.conn","state":"signed_out","why":"…"}` | No token yet ("not logged in"), a logout, or the instance refused the token (4001), which is forgotten. The app asks for a login |
| `{"t":"core.conn","state":"update_needed","why":"…"}` | No protocol version in common (4002) |
| `{"t":"core.conn","state":"connecting","why":"moving to …"}` | A signed `moved` frame came, and the core waits for the new place to answer with the same key |
| `{"t":"core.moved","from":"…","address":"…"}` | The instance moved, and the core is connecting at its new address, with the same token, cache and cursor |
| `{"t":"error","code":"moved_unsigned"}`, `{"t":"error","code":"moved_elsewhere"}` | A `moved` frame not signed with the instance's key, or a new place with another key: the core stays where it is |
| `{"t":"core.offer","address":"https://…","code":"loom-link-…","username":"elliot"}` | An agent's `add_server` was allowed on this device (`server.offered` with its `by`), or an install the person allowed here put loom on one of their hosts, so this app adds the server: with `code`, signed in with it (`link`, above, to a core for that server), and without, for the person to sign in to. Only for an event the cache hadn't applied, or once for each install, so once |
| `{"t":"core.login","id":"l_1","ok":true,"user":"u_1","device":"d_3","kept":true}` | Logged in, and connecting. `kept` is false, with `why`, when the credential store couldn't keep the token, so the next start asks again |
| `{"t":"core.login","id":"l_1","error":{"code":"bad_password","message":"…","retry_after":60}}` | The login failed: the instance's error code, `unreachable`, `bad_server` or `busy`. `retry_after` comes with `rate_limited` |
| `{"t":"error","code":"keyring","message":"…"}` | The credential store couldn't be read at start |
| `{"t":"core.queued","cid":"m_…","conversation":"c_9","text":"…","at":…}` | A `send` is in the outbox. The `ack` with its `cid` follows once the instance has it |
| `{"t":"core.data","id":"g_1","what":"messages","items":[…],"more":true}` | The answer to `core.get`, oldest first for messages. `more` says the cache has older ones |
| `{"t":"core.notify","title":"Builder","body":"…","agent":"a_2","conversation":"c_9","kind":"run.finished"}` | Worth a system notification: a reply that finished or failed, or a question waiting (`approval.needed`), only while no one is looking; and, looking or not, an agent's `notify` or a routine's reply (`kind: "notify"`, with the routine's `conversation`), or one from loom itself, with no agent and its title alone. Only for live events, not for catch-up |
| `{"t":"core.file","id":"u_1","file":{"file":"9f86d0…","name":"shot.png","mime":"image/png","size":48213}}` | A `file.upload` went up. For a `file.get`, `"path":"…"` instead: where the file is. Either can have `error`, with `code` and `message`, instead |
| `{"t":"core.device_ask","call":"tc_5","tool":"screenshot","args":{}}` | An agent's device call that needs the system: `screenshot`, `read_clipboard` or `write_clipboard` (`args.text`). The core has checked it is on, and for one that asks, that this device signed the yes. The app answers with `device.answer` |
| `{"t":"core.device","tools":{"run_command":"ask",…},"hosts":[{"name":"vps","target":"root@vps","via":"ssh","mode":"ask"}]}` | What this device offers agents: each tool's mode, and the person's hosts with each one's. To `device.get`, `device.tools` and each change to the hosts |
| `{"t":"core.hosts_found","found":[{"name":"box","target":"box","via":"tailscale"}]}` | The answer to `hosts.scan` |
| `{"t":"core.update","version":"0.3.0","path":"C:\\Users\\…\\update\\0.3.0\\loom.exe","notes":"…"}` | A newer release is downloaded and checked, at `path`. To an `update.check` that found nothing new, `"latest":true` and this version instead, or `error` |
| `{"t":"core.release","version":"0.2.1"}` | The updater read a release's manifest, and its signature checks: its version, newer than the app or not, for the app to hand to its other servers' cores as `release` |
| `{"t":"core.server","server":"…","loom":"0.2.0","latest":"0.2.1","behind":true,"may":true,"can":true,"update":{"state":"waiting"}}` | The instance's version, from `welcome`, and the newest release's, once the core knows both: on each `welcome` and each `release`, and as its update goes. `behind` is whether the release is newer, by `shared/release.calx`'s rule, and never for the instance in the app, which updates with the app ([protocol.md](../protocol/protocol.md#updating-the-instance)). An instance that's behind is asked `instance.updates` once on each connection: `may` is whether this person may update it, `can` whether it can update itself where it runs, with `why` when it can't, and `update` its update under way (`asked`, `downloading`, `waiting`, `restarting` or `failed`, with `why`). Once it says `restarting`, the core tries again every second for two minutes rather than backing off |
| `{"t":"core.updates","devices":[{"device":"app","kind":"app","version":"0.2.0","latest":"0.2.1","may":true,"can":true,"state":""}],"all":true}` | From the first core, when it changes: each device that's behind, or whose update is under way or failed. `device` is `"app"` or a server's folder, `kind` `app` or `server`, `version` what it runs, `latest` the new one, `may`, `can` and `why` as in `core.server`, `state` its update under way and `error` why one failed. `all` is whether updating everything has something to do. The update icon shows while `devices` isn't empty |
| `{"t":"core.relay","to":"servers/2","frame":{"t":"server.update"}}` | From the first core: hand `frame` to the core of the server whose folder is `to` |
| `{"t":"core.restart","version":"0.2.1","path":"C:\\Users\\…\\update\\0.2.1\\loom-setup.exe"}` | From the first core: the app updates now, through the setup at `path`, and quits. For updating everything, it comes once each server's update has gone far enough to finish on its own (waiting, restarting, failed or done), or after two minutes |
| `{"t":"error","code":"offline","for":"q_2"}` | A frame other than `send` came while the core wasn't connected, so it didn't go |
| `{"t":"error","code":"not_sent","ref":"m_…","message":"…"}` | A send to an agent the instance couldn't make a conversation with, such as one deleted meanwhile. It leaves the outbox |
| `{"t":"error","code":"cache","message":"…"}` | The cache couldn't be read or written. An event that wasn't applied isn't in the cursor either, so the next connection gets it again |
| `{"t":"error","code":"bad_config","message":"…"}` | The config's `server` isn't an `http://` or `https://` address |
| `{"t":"error","code":"local","message":"…"}` | The instance on this computer didn't start, in `"mode": "local"`. The core waits for a login, as without a server |

Each `core.conn` also has `server`, the instance's address, once the core has one, so an app signed in to several tells them apart.

A connection that died without a close, as a sleeping laptop's does, is noticed after 45 s with nothing from the instance (the socket pings after 25 s of quiet and waits 20 s more), and the core reconnects.

[`tests/protocol/core_conn.calx`](../tests/protocol/core_conn.calx) runs the connection against a real instance.
