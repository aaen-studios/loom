# desktop

Rust: the GPUI app for Windows and macOS. It draws screens and reaches the system (tray, notifications, starting at login, screenshots, the clipboard, the updater), and leaves everything else to the [core](../core/), which it links.

GPUI comes from GPUI Kit (`gpui-kit`), pinned exactly in `Cargo.toml`. See [PLAN.md: Desktop on GPUI](../PLAN.md#desktop-on-gpui-what-to-know).

## Building

You need a recent stable Rust (`rustup update stable`) and `calx` on PATH. `build.rs` builds the core (`core/lib.calx`) into a static library with `calx build --staticlib` and links it, so `cargo` is the only command:

```sh
cargo run --release
```

Set `CALX` to use a different `calx` binary.

### On a Mac

Apple silicon, with Xcode's command line tools. `cargo run --release` works there too, but macOS gives notifications only to an app with a bundle, so to run loom as a release does, make its `loom.app` (and its disk image, if you want it), from the repository's root:

```sh
(cd desktop && LOOM_VERSION=0.0.1-dev cargo build --release)
calx scripts/mac.calx app desktop/target/release/loom 0.0.1-dev build/mac
calx scripts/mac.calx dmg build/mac/loom.app build/mac/loom-mac.dmg
open build/mac/loom.app
```

The bundle is signed ad hoc, as a release's is. Opened from anywhere but Applications, it doesn't start at login, and from its disk image it doesn't update itself. `calx tests/setup/mac.calx build/mac/loom.app` tries its updates from end to end, in a folder of its own.

## What's here

- `src/main.rs`: starts GPUI, loads Geist (in `assets/fonts`, under the OFL), puts GPUI Kit's widgets in loom's colours, and opens the window with loom's own title bar.
- `src/core.rs`: the core's C boundary. Its events come on the core's thread and go to the window over a channel, and a browser's frames, the JPEG as it came, over one of their own, of which the window takes the newest.
- `src/model.rs`: what the screens show, as the core tells it. Lists come from the core's cache with `core.get` and are fetched again when an event says they changed. Only a reply still being written lives here alone, from its deltas. The unread dots come from what the instance keeps read in each conversation against when its newest reply is from, and opening a chat, or a reply coming while it is open, marks it read with `conversation.read`.
- `src/app.rs`: the window. It has the sidebar, under the knot and the wordmark, grouped as the core says (`core/sidebar.calx`, `src/model/sidebar.rs`): the pinned tiles, three across with each row centred, Waiting on you, each with what it asks under its name and a warm dot, a thin line, then one list of agents and group chats in the person's order with the person's folders in it, each opened and shut from its name and renamed there in place, + New (New group chat, New agent and New folder, which a right-click on empty space or on a folder has too), and Hidden · N, shut until opened; a row drags into a new place, faded where it was while a lifted copy follows the pointer and a line in the accent colour shows where it lands, or onto a folder's name, which it goes in, and a tile drags among the tiles (`droppable`, `tile_drop`, `Model::drop_item`, `sidebar.order`); an agent whose reply came while its chat wasn't open is bold until it is, and the open agent has a row under it for each other agent's thread with it ("From Casper", by Casper's thread), which opens it in the chat's place to read, with **Continue in your own chat** where the composer would be (`continue_button`), whose reply marks it and puts a dot of Casper's colour on the agent's row while the agent isn't open, and one the same for each thread an agent made beside its chat with `conversation.create`, by its title and the maker's thread, which the person writes in too (`Model::asks`; ## Trying it

Run an instance (`calx server/main.calx serve`), then start the app and sign in with its address, a username, a password and, the first time, the setup code it printed. Or choose **Run one on this computer** on the sign-in page: the app keeps that choice in `mode` in its data folder, and runs the instance itself from then on, with its data in `instance` there. **Sign out** goes back to the sign-in page and stops it; its agents and chats stay for next time. While developing:

- `LOOM_SERVER`: an instance's address, filled in on the sign-in page.
- `LOOM_DATA`: the folder for the core's cache, instead of `%APPDATA%\Loom` (`~/Library/Application Support/Loom` on a Mac). A build from source on the same folder as the installed loom only brings that loom forward (`src/single.rs`), so give it a folder of its own to run beside it.
- `LOOM_THEME`: `dark` or `light`, instead of following the system.
- `LOOM_UPDATE`: a release manifest's address, for trying updates in a build from source, which doesn't update itself otherwise.
- `LOOM_UPDATE_KEY`: the public key, in hex, a test's releases at `LOOM_UPDATE` are signed with. And `LOOM_TOKEN`: a device token to start with, instead of signing in. A build from source alone reads them.

## Measuring

`cargo build --release --features perf` builds an app that measures itself (`src/perf.rs`) and opens its window far off screen, where it can never be the window in front, rather than where the window was last, and leaves that place in `window.json` alone. Each second it draws anything, it adds a line to `perf.log` in its data folder: frames a second, the average and longest frame (from the start of `render` to the end of painting), and the time in each timed step: `render` (building the window's elements, the rest of a frame being GPUI's layout and painting), `chat`, `take` (a frame from the core), `rows` (rebuilding the chat's rows), a count of each thing that asked for another frame (`want:app`, `want:motion`, `want:thread`, `want:threads`, `want:yarn`), and a count of the views built rather than drawn from their cache: `list` (the chat's list), `row` (a finished message in it) and `sidebar`. It also says when the core started, the first frame and the chat came. [`tests/bench/desktop.calx`](../tests/bench/desktop.calx) makes a data folder with a long chat to start it on, streams a reply into it while it runs, and gives it 500 routines, skills and activity entries for the pages that list them. Without the feature, none of this is built.

## Releases

A tag like `v0.3.0` runs `.github/workflows/release.yml`. It builds `loom.exe` with the version in it (`LOOM_VERSION`) and [`setup/`](setup/), loom's own installer and updater, then `scripts/release.calx pack` puts `loom.exe` into the setup as `loom-setup.exe`, under a header signed with the release key. It also builds the server for Linux, Windows and macOS, and publishes them all with a `manifest.json` that `scripts/release.calx` signs with the same key, from the CI secret `LOOM_RELEASE_KEY`. The tag's message is the release notes.

`loom-setup.exe` puts loom in `%LOCALAPPDATA%\Programs\loom`, for the person alone, with no administrator, and gives its Start menu shortcut the AppUserModelID `AaenStudios.Loom`, so notifications show as loom. From then on loom updates itself: the core finds a newer release, downloads its `loom-setup.exe` and checks it against the signed manifest, and the sidebar offers "Restart to update" (or it goes in on its own while loom is in the tray and no agent works, if the person turned that on). `shell::apply_update` hands the setup over with `--update` and the app quits. The setup checks its own signature again, swaps `loom.exe`, starts the new one and watches it start, and puts the old one back if it doesn't. "Check for updates" in the tray looks at once. On a Mac the release builds `loom` the same way, and `scripts/mac.calx` makes `loom.app` (its Info.plist, the icon, an ad-hoc signature) and `loom-mac.dmg`, which the manifest names as `macos-desktop`. The core downloads a newer release's disk image and checks it the same way, and `shell::apply_update` hands over to it through `src/swap.rs`.
