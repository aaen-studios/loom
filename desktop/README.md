# desktop

Rust: the GPUI app for Windows and macOS. It draws screens and reaches the system (tray, notifications, starting at login, screenshots, the clipboard, the updater), and leaves everything else to the [core](../core/), which it links.

GPUI comes from GPUI Kit (`gpui-kit`), pinned exactly in `Cargo.toml`. See [PLAN.md: Desktop on GPUI](../PLAN.md#desktop-on-gpui-what-to-know).

## Building

You need a recent stable Rust (`rustup update stable`) and `calx` on PATH. `build.rs` builds the core (`core/lib.calx`) into a static library with `calx build --staticlib` and links it, so `cargo` is the only command:

```sh
cargo run --release
```

Set `CALX` to use a different `calx` binary.

## What's here

- `src/main.rs`: starts GPUI, loads Geist (in `assets/fonts`, under the OFL), puts GPUI Kit's widgets in loom's colours, and opens the window with loom's own title bar.
- `src/core.rs`: the core's C boundary. Its events come on the core's thread and go to the window over a channel.
- `src/model.rs`: what the screens show, as the core tells it. Lists come from the core's cache with `core.get` and are fetched again when an event says they changed. Only a reply still being written lives here alone, from its deltas.
- `src/app.rs`: the window. It has the sidebar of agents, under the knot and the wordmark, where an agent whose reply came while its chat wasn't open is bold until it is, the header with the agent's menu and its permission mode, and the chat. The chat is never swapped out for another page: an agent's own pages open in a panel beside it on the right, where its browser shows too, under its thread, which fidgets while the agent is idle: a thinking loop, a knot or a twang every few seconds (its edit page, with its name, its instructions and every revision to go back to; its activity page: what it ran, what it was allowed, and what changed; and its memory page: its notes and the shared ones, to add to or delete), and everything else opens in a popup over the window, its pages down its left. At the foot of the sidebar the server is a spool, its thread coming off it the way an agent is its thread: wound and still while it's connected, turning while it connects, and unwound with its end hanging loose while it can't be reached (`thread::spool`), with the words beside it only while it isn't well. The app signs in to several servers, each with a core of its own and its own folder under `servers/` (kept in `server-list`): each is a spool in that row, the one on screen bigger, another coming on screen when clicked, with a dot when one of its agents said something. The server popup's **Add a server** signs in beside the one on screen, and **Sign out and remove** takes one away. When an agent's `add_server` is allowed here (`server.offered`), Add a server opens with its address in. **Settings**, at the other end of the row from the spool, opens the popup at the person's pages, and the spool at the server's. **About you** is the person's profile, which every agent starts with, to edit. **Routines** lists the routines, with when each runs next and how its last run went, to make, change, pause, run now or delete, and with a webhook, its address and secret to copy. A message a routine sent shows "From the routine …" in the chat. **Skills** lists the person's skills, to add, change or delete, and **Agent programs** lists the instance's ACP agents, with their settings, and their settings shared with everyone else, a number of tokens each a day or a month (or for a member, what's left of theirs), and the ACP Registry's, to install, update or remove. **MCP servers** sets up the person's MCP servers and the keys they use, which each agent picks on its edit page. **Plugins** lists the person's plugins, with what each asks for and Allow for what waits, and opens a plugin's panel beside the chat (`src/panel.rs`), which shrinks to nothing while the popup is open, since a web view draws over everything in the window. It answers the panel's door: `data.get` and `data.put` with the plugin's data, and `cmd` for a command the plugin asked for and the person allowed. **This PC** (when the instance is somewhere else) sets what agents may do on this computer: run commands, read files, list folders, open things, take screenshots and use the clipboard, each off, ask or allow. It does the screenshots (with `xcap`) and the clipboard when the core asks (`core.device_ask`). **People** (for an instance somewhere else) lists everyone with an account, to make one an admin, make them a password reset link, or remove them, and the invites still open, and makes an invite: a member or an admin, with its link to copy. **Add a phone** draws the QR code a phone scans to join the account (with `qrcode`), says when it has, and lists the devices signed in, to sign one out. On an instance somewhere else it can also delete the account, after asking (`account.delete`). For the instance in the app, it first asks to let phones reach this computer (`instance.phones`), and can stop them again. The chat shows replies, thoughts, tool calls, questions, files and pictures, and the composer, which takes files from the paperclip, dropped on the chat, or pasted (an image, or files copied in Explorer). Search in the sidebar finds words in every chat, and in file names. Every launch opens with the threads drawing in, the name rising among them and sinking away, and the window closing on their one line to show the app (`splash`). The welcome, with the threads woven through the name, starts the instance here or signs in to a server, and making the first agent fills the window too: pick a brain (an agent program, as a tile whose thread moves under the pointer), a name and a colour, and the threads weave it together, then the window closes on its thread into its chat. Another agent, from the sidebar's +, is made the same way beside the sidebar. A page beside the sidebar unrolls under a thread passing down it, in the agent's colour for a chat. An agent's empty chat twangs its thread hello, thinks along while the person types to it, and brings its suggestions in one by one. While an agent's browser is open, a **Browser** button in its header shows the page beside the chat as it changes (`browser.watch`, `browser.frame`), and **Take over** gives the person the page: their clicks, scrolls and keys go to it (`browser.input`) until **Hand back**. When the agent asks for them (`browser_ask_person`), a card above the composer says what for and opens it, and when it asks for something only they should know (`browser_ask_secret`), a masked box there sends it straight into the page (`browser.secret`). A message sent while the agent is still answering waits above the composer (`queue.changed`), where each can go now (steer), move up, be edited or be dropped. **Tasks** in Settings starts a long job for an agent, in a conversation of its own, and lists every task with what it's doing, to pause, resume, cancel or try again. Opening one shows its conversation in the chat, under a strip with its title, its status and a way back to the agent's chat (`task.updated`). Esc steps back: out of a menu, the popup, the panel beside the chat, the server form, or a step of making an agent. Threads ease between moods and colours (`thread.rs` keeps each one's last under a key), small things fade in, and screens change through the threads, never by fading. A chat with nothing in it yet puts the composer in the middle, under the agent's thread and name, with a few things to ask. Menus are an icon and a title, with no explanations under them. The look follows `design/explorations/round-4.html`, with every value from `design/tokens.toml` (`design/generated/tokens.rs`).
- `src/thread.rs`: an agent's thread, drawn as one path that moves with what the agent is doing.
- `src/shell.rs`: the tray (Open, Start at login, Quit), Windows notifications for what the core says is worth one, starting at login with `--background`, and hiding the window to the tray when it's closed. A tick that comes long after the last means the computer slept, so the app tells the core (`app.wake`). It also turns a pasted bitmap into a PNG.
- `src/panel.rs`: panels (PLAN.md, "The panel sandbox"), each in a WebView2 web view of its own over the window, through `wry`. A panel loads from its own scheme and origin (`panel-<id>`), and its pages come with a content security policy that lets them load only their own files. WebView2 also answers every other request with 403 before it reaches the network, and the browser sends whatever's left to a proxy that isn't there and looks up no host name. Navigation away, new windows, permissions, downloads and drops are refused. A prelude in every frame takes away the web view's storage and WebRTC, which nothing else stops in WebView2, and gives the panel `loom.send(op, args)`: the one door, whose messages the app checks.
- `src/panel_test.rs`: `loom --panel-test OUT`, the break-out test CI runs. It shows `panels/breakout`, a panel that tries 30 ways out (fetch, XHR, WebSocket, images, scripts, frames, workers, forms, windows, WebRTC in its own window and a blank frame's, storage, the core through the door, navigating away), while listening on a TCP and a UDP port of this machine that the panel aims at. It passes when every attempt is stopped and nothing reaches the listeners.

Not here yet: the updater (LOO-29), the instance in the app (LOO-27), and files, images and search (LOO-28).

## Trying it

Run an instance (`calx server/main.calx serve`), then start the app and sign in with its address, a username, a password and, the first time, the setup code it printed. Or choose **Run one on this computer** on the sign-in page: the app keeps that choice in `mode` in its data folder, and runs the instance itself from then on, with its data in `instance` there. **Sign out** goes back to the sign-in page and stops it; its agents and chats stay for next time. While developing:

- `LOOM_SERVER`: an instance's address, filled in on the sign-in page.
- `LOOM_DATA`: the folder for the core's cache, instead of `%APPDATA%\Loom`.
- `LOOM_THEME`: `dark` or `light`, instead of following the system.
- `LOOM_UPDATE`: a release manifest's address, for trying updates in a build from source, which doesn't update itself otherwise.

## Releases

A tag like `v0.3.0` runs `.github/workflows/release.yml`. It builds `loom.exe` with the version in it (`LOOM_VERSION`), and `loom-setup.exe` from `installer.iss` with Inno Setup. It also builds the server for Linux and Windows, and publishes them all with a `manifest.json` that `scripts/release.calx` signs with the release key, from the CI secret `LOOM_RELEASE_KEY`. The tag's message is the release notes.

The installer puts loom in `%LOCALAPPDATA%\Programs\loom`, for the person alone, and gives its Start menu shortcut the AppUserModelID `AaenStudios.Loom`, so notifications show as loom. From then on loom updates itself. The core finds and checks a release, the sidebar offers "Restart to update", and `shell::apply_update` renames the running `loom.exe` to `loom.old.exe`, puts the new one in its place and starts it. The new one waits for the old one to end, then removes it. "Check for updates" in the tray looks at once.
