# desktop

Rust: the GPUI app for Windows and macOS. It draws screens and reaches the system (tray, notifications, starting at login, screenshots, the clipboard, the updater), and leaves everything else to the [core](../core/), which it links.

GPUI comes from GPUI Kit (`gpui-kit`), pinned exactly in `Cargo.toml`. See [PLAN.md: Desktop on GPUI](../PLAN.md#desktop-on-gpui-what-to-know).

## Building

You need a recent stable Rust (`rustup update stable`) and `calx` on PATH. `build.rs` builds the core (`core/lib.calx`) into a static library with `calx build --staticlib` and links it, so `cargo` is the only command:

```sh
cargo run --release
```

Set `CALX` to use a different `calx` binary.

### On a Mac

Apple silicon, with Xcode's command line tools. `cargo run --release` works there too, but macOS gives notifications only to an app with a bundle, so to run loom as a release does, make its `loom.app` (and its disk image, if you want it), from the repository's root:

```sh
(cd desktop && LOOM_VERSION=0.0.1-dev cargo build --release)
calx scripts/mac.calx app desktop/target/release/loom 0.0.1-dev build/mac
calx scripts/mac.calx dmg build/mac/loom.app build/mac/loom-mac.dmg
open build/mac/loom.app
```

The bundle is signed ad hoc, as a release's is. Opened from anywhere but Applications, it doesn't start at login, and from its disk image it doesn't update itself. `calx tests/setup/mac.calx build/mac/loom.app` tries its updates from end to end, in a folder of its own.

## What's here

- `src/main.rs`: starts GPUI, loads Geist (in `assets/fonts`, under the OFL), puts GPUI Kit's widgets in loom's colours, and opens the window with loom's own title bar.
- `src/core.rs`: the core's C boundary. Its events come on the core's thread and go to the window over a channel, and a browser's frames, the JPEG as it came, over one of their own, of which the window takes the newest.
- `src/model.rs`: what the screens show, as the core tells it. Lists come from the core's cache with `core.get` and are fetched again when an event says they changed. Only a reply still being written lives here alone, from its deltas.
- `src/app.rs`: the window. It has the sidebar of agents, under the knot and the wordmark, grouped as the core says (`core/sidebar.calx`): Waiting on you, the pinned tiles, the rest, the person's folders, each opened and shut from its name and renamed there in place, and Hidden, shut until opened; an agent whose reply came while its chat wasn't open is bold until it is, and the open agent has a row under it for each other agent's thread with it ("From Casper", by Casper's thread), whose reply marks it and puts a dot of Casper's colour on the agent's row while the agent isn't open, the header with the agent's menu, its brain chip (its program's icon and what it's set to, such as "Opus 5.5 · Medium", which opens one menu under it with its model and its effort, the person's default marked on one of each) and its permission mode, and the chat. The chat is never swapped out for another page: an agent's own pages open in a panel beside it on the right, where its browser shows too, under its thread, which fidgets while the agent is idle: a thinking loop, a knot or a twang every few seconds (its edit page, under the thread with its colour beneath it, twelve of loom's, then a small colour wheel for its own, which opens a bigger wheel in a popup to pick from, with a field for one as #rrggbb, then its name and its instructions; its model, effort, permission, what a message while it answers does and its backup, each a row of chips with the person's default marked as one of them, which it follows while that one is on; what it knows, what it did (its activity) and its routines; every revision to go back to; and where it runs: Isolated, in a sandbox, which a member's agents always are and an instance without sandboxes can't be, and its network from there, Everything, Only these hosts (an editor that adds and removes them) or Nothing; its activity page: what it ran, what it was allowed, and what changed; and its memory page: its notes and the shared ones, to add to or delete), and everything else opens in a popup over the window, its pages down its left. At the foot of the sidebar is the server, as a soft ball of yarn: pale in its colour, with a few strands of it wound round, both chosen from its name, so each server looks like itself (`thread::yarn`). It rests while it's connected, its strands turn while it connects, it greys while it can't be reached, and signed out it's a dashed ring, with its name and how it is beside it. The app signs in to several servers, each with a core of its own and its own folder under `servers/` (kept in `server-list`): each is its yarn in that row, the one on screen with its name, another coming on screen when clicked, with a dot when one of its agents said something. The server popup's first page has a **Name** for the server, the person's own on this device and kept in `prefs.json` by its address (empty is the address, and its yarn keeps the address's colour), and says the server's version, and quietly, a newer loom that's out (a small ring on its yarn in the sidebar too, from the core's `core.server`) or an update under way, with **Update** (or **Now** while one waits, and **Try again** after one failed) for an owner or admin, and to the owner, **Updates itself**, a switch (`instance.updates`). It also has **Scripts**: turned on, it shows the script token once, to copy, with the `loom ask` line to try, and it makes a new one or turns them off (`scripts.get`, `scripts.on`, `scripts.off`). Under it, **Status token** makes a token that only reads the status, for a dashboard, shown once to copy, or a new one, or revokes it (`scripts.status_on`, `scripts.status_off`). One an agent had saved to a file (`token.make_to_file`) says "Saved to <path> by <agent>" there instead. Its **Add a server** signs in beside the one on screen, and **Sign out and remove** takes one away. The first server, whose core updates the app, leaves the sidebar when it's signed in nowhere and isn't the instance here while there are others (`first_out`; the instance here goes with **Stop and remove**), and **Add a server** then has **Run here** to start the instance on this computer again. - `src/rules.rs`: the Rules page in the popup: the rules, the new-rule form and the what-if.
- `src/thread.rs`: an agent's thread, drawn as one path that moves with what the agent is doing.
- `src/autoscroll.rs`: the middle button's scrolling, as Chrome and Edge have it. Pressed in the chat (a box of details in it included), but not on anything there with the pointing hand (a link, a pill, a button), or anywhere in the sidebar, whose rows all have the hand, it leaves a small see-through marker, and what's under the marker scrolls each frame, by the time the frame took. The speed is Chromium's (`autoscroll_controller.cc`, with the 5000 of `fixed_velocity_curve.cc`): nothing within 15 px of the marker, up or down, then 0.04 × d^2.2 pixels a second for the pointer d px away, d counted from the marker: about 70 px/s at 30 px, 220 at 50, 1,000 at 100, 4,600 at 200 and 11,000 at 300, with no top speed. A frame counts as 50 ms at most, so a late one doesn't jump. The cursor is the system's pan cursor (Windows' own, from user32; on a Mac, drawn the same in `vendor/gpui-pre-macos`, at 1× and 2×): up and down at rest within the 15 px, an arrow up or down once it scrolls. The pointer leaving those 15 px with the button still down makes it a drag, which stops when let go; let go within them, it stays on until a click, a key (Esc only stops it) or the wheel.
- `src/shell.rs`: the tray (Open, Start at login, Quit), in the menu bar on a Mac, notifications for what the core says is worth one (toasts on Windows; on a Mac, `UNUserNotificationCenter`'s, with its sound in the notification, posted from the window's task by `src/mac.rs`), the composer's dictation (Windows+H, or a Mac's `startDictation:`), starting at login with `--background` (a Run key on Windows and a LaunchAgent on a Mac; an installed release turns it on at its first start; a dev or `perf` build, one outside `%LOCALAPPDATA%\Programs\loom` or a Mac's Applications, or one started with `LOOM_DATA` or `LOOM_SETUP_SANDBOX` never does, and "Start at login" in one of those points the entry at the installed loom when there is one; it shows as on only while the entry starts that program), hiding the window to the tray when it's closed, and putting the window back where it was (`put_window`, `window_place`). A tick that comes long after the last means the computer slept, so the app tells the core (`app.wake`). It also turns a pasted bitmap into a PNG.
- `src/mac.rs`: what's the Mac's own, through AppKit (`objc2`): showing and hiding the window, putting it back where it was, keeping the Mac awake while an agent works, starting dictation, posting notifications and hearing their clicks (`UNUserNotificationCenter`, with its own delegate, so a notification sounds while loom is in front too), the PATH the person's login shell sets (an app opened from the Finder or at login gets only the system's), and whether loom can update itself where it runs. `src/main.rs` gives the Mac its menu bar: loom's, Edit's and Window's usual items and keys.
- `src/swap.rs`: a Mac's update. The old loom copies the new `loom.app` out of the release's disk image and starts its loom with `--swap`, which waits for the old one to end, moves the old bundle aside, puts itself in its place and starts from there. If that loom ends with an error within ten seconds, the old bundle goes back and starts again. It says what it did in `update.log`.
- `src/single.rs`: one loom to a data folder. The loom running owns a named mutex for its folder in the Windows session (`Local\loom-<hash of the folder>`), and loom started again while it runs (from the Start menu while it's in the tray, after a background update, or from a second shortcut) asks that loom to show its window, out of the tray, and ends. Started with `--background`, it asks for nothing to be shown. A loom quitting lets go before its cores stop, and one started then waits up to 20 s for it, then runs. On macOS a lock on `loom.lock` in the folder keeps the one loom, and the system brings the running app forward.
- `src/place.rs`: where the window was. loom opens where it was closed, the same size, maximized if it was, kept in `window.json` each time the window moves or resizes, so a crash or an update keeps it too. A place whose title bar is on no screen now, as when a monitor was unplugged, comes back centered on the screen it overlapped most, or the main one, made to fit. Started in the tray, the window is hidden before it's put there, so it never shows for a moment at login.
- `src/panel.rs`: panels (PLAN.md, "The panel sandbox"), each in a web view of its own over the window, through `wry`: WebView2 on Windows, WKWebView on a Mac. A panel loads from its own scheme and origin (`panel-<id>`), and its pages come with a content security policy that lets them load only their own files and sandboxes them with scripts, so a page's origin is no one's, and so is each blank frame's, which it can't reach into. WebView2 also answers every other request with 403 before it reaches the network, and the browser sends whatever's left to a proxy that isn't there and looks up no host name. On a Mac, WebKit's private `_allowedNetworkHosts` is an empty set, so the web view reaches no host over HTTP or WebSockets, not even the one a clicked link connects to ahead of time, and a macOS without it opens no panels. Its data store keeps nothing, connects ahead to nothing (the private `allowsServerPreconnect`, where there is one) and sends what's left to the same missing proxy (from macOS 14), a content rule list blocks every load but the panel's own, and it opens no windows from scripts, checks nothing with Safe Browsing and has no AirPlay. Navigation away, new windows, permissions, downloads and drops are refused. A prelude in every frame that loads takes away the web view's storage and WebRTC, which nothing else stops in WebView2, cancels a click on a link out of the panel, which WebKit would connect to as it's clicked, and gives the panel `loom.send(op, args)`: the one door, whose messages the app checks.- `src/panel_test.rs`: `loom --panel-test OUT`, the break-out test CI runs on Windows and on the Mac. It shows `panels/breakout`, a panel that tries 32 ways out (fetch, XHR, WebSocket, images, scripts, frames, workers, forms, windows, links, links in closed shadow roots its HTML declares, WebRTC in its own window and a blank frame's, storage, the core through the door, navigating away), while listening on a TCP and a UDP port of this machine that the panel aims at, in a window off screen (and clear, on a Mac) that never takes focus. It passes when every attempt is stopped and nothing reaches the listeners.
- [`setup/`](setup/): `loom-setup.exe`, loom's installer, updater and uninstaller, a program of its own, drawn by hand in loom's look rather than with GPUI so it stays small and opens at once.


## Trying it

Run an instance (`calx server/main.calx serve`), then start the app and sign in with its address, a username, a password and, the first time, the setup code it printed. Or choose **Run one on this computer** on the sign-in page: the app keeps that choice in `mode` in its data folder, and runs the instance itself from then on, with its data in `instance` there. **Sign out** goes back to the sign-in page and stops it; its agents and chats stay for next time. While developing:

- `LOOM_SERVER`: an instance's address, filled in on the sign-in page.
- `LOOM_DATA`: the folder for the core's cache, instead of `%APPDATA%\Loom` (`~/Library/Application Support/Loom` on a Mac). A build from source on the same folder as the installed loom only brings that loom forward (`src/single.rs`), so give it a folder of its own to run beside it.
- `LOOM_THEME`: `dark` or `light`, instead of following the system.
- `LOOM_UPDATE`: a release manifest's address, for trying updates in a build from source, which doesn't update itself otherwise.
- `LOOM_UPDATE_KEY`: the public key, in hex, a test's releases at `LOOM_UPDATE` are signed with. And `LOOM_TOKEN`: a device token to start with, instead of signing in. A build from source alone reads them.

## Measuring

`cargo build --release --features perf` builds an app that measures itself (`src/perf.rs`) and opens its window far off screen, where it can never be the window in front, rather than where the window was last, and leaves that place in `window.json` alone. Each second it draws anything, it adds a line to `perf.log` in its data folder: frames a second, the average and longest frame (from the start of `render` to the end of painting), and the time in each timed step: `render` (building the window's elements, the rest of a frame being GPUI's layout and painting), `chat`, `take` (a frame from the core), `rows` (rebuilding the chat's rows), a count of each thing that asked for another frame (`want:app`, `want:motion`, `want:thread`, `want:threads`, `want:yarn`), and a count of the views built rather than drawn from their cache: `list` (the chat's list), `row` (a finished message in it) and `sidebar`. It also says when the core started, the first frame and the chat came. [`tests/bench/desktop.calx`](../tests/bench/desktop.calx) makes a data folder with a long chat to start it on, streams a reply into it while it runs, and gives it 500 routines, skills and activity entries for the pages that list them. Without the feature, none of this is built.

## Releases

A tag like `v0.3.0` runs `.github/workflows/release.yml`. It builds `loom.exe` with the version in it (`LOOM_VERSION`) and [`setup/`](setup/), loom's own installer and updater, then `scripts/release.calx pack` puts `loom.exe` into the setup as `loom-setup.exe`, under a header signed with the release key. It also builds the server for Linux, Windows and macOS, and publishes them all with a `manifest.json` that `scripts/release.calx` signs with the same key, from the CI secret `LOOM_RELEASE_KEY`. The tag's message is the release notes.

`loom-setup.exe` puts loom in `%LOCALAPPDATA%\Programs\loom`, for the person alone, with no administrator, and gives its Start menu shortcut the AppUserModelID `AaenStudios.Loom`, so notifications show as loom. From then on loom updates itself: the core finds a newer release, downloads its `loom-setup.exe` and checks it against the signed manifest, and the sidebar offers "Restart to update" (or it goes in on its own while loom is in the tray and no agent works, if the person turned that on). `shell::apply_update` hands the setup over with `--update` and the app quits. The setup checks its own signature again, swaps `loom.exe`, starts the new one and watches it start, and puts the old one back if it doesn't. "Check for updates" in the tray looks at once. See [setup/README.md](setup/README.md).

On a Mac the release builds `loom` the same way, and `scripts/mac.calx` makes `loom.app` (its Info.plist, the icon, an ad-hoc signature) and `loom-mac.dmg`, which the manifest names as `macos-desktop`. The core downloads a newer release's disk image and checks it the same way, and `shell::apply_update` hands over to it through `src/swap.rs`.
