# server

Calx: the instance, and the `loom` program.

- [`main.calx`](main.calx): the `loom` command line: `serve`, `user add`, `user list`, `acp add`, `acp list`, `acp install` (an agent program from the ACP Registry, with `--env NAME=value` settings, saying plainly what to install when it needs npx or uvx that aren't there) and `acp settings` (sealed, `NAME=` removes one), both straight on the data folder, `files limit`, `push key` (the APNs key, kept sealed) and `push off`, `link` (a [link code](../protocol/protocol.md#link-codes) for an agent's `add_server`: the owner's on a new instance, else NAME's or the owner's), `ask`, `routine run`, `approvals` and `approve` (the person's scripts, through the running instance's `/api/scripts/`, with their script token; `import` with none, where it can open `--data`, makes itself one that only imports, for 15 minutes), `status` (which also says the user it runs as and whether push is on), `update` (`server/update.calx`; a running instance takes it once it restarts, as the app's Update does by itself), `mcp` and `version`. `serve` won't run as root or an elevated Administrator unless given `--allow-root`, and the tests pass it, since GitHub's Windows runners are elevated. Every command but `serve` and `mcp` takes `--json`, and answers with one JSON object, or `{"error":{"code","message"}}` and a non-zero exit, so an agent over SSH reads it reliably. `install` sets loom up on a server (below). `import openbot --from-user USER`, as root, stages OpenBot's data from that user's folder into the instance's `imports/` ([`stage.calx`](stage.calx)) and waits for the instance to import it for its owner, or leaves it for the owner's setup. Files root writes in a data folder are given to the folder's owner, so the service can use them. Later `loom receive`.
- [`mcp.calx`](mcp.calx): `loom mcp`, loom's own tools as an MCP server on standard input and output. The instance gives it to every agent's session, and it hands each call back to the instance. The tools are in [`shared/tools.calx`](../shared/tools.calx). In Code Mode (PLAN.md, "Code Mode") it offers `search_tools` and `run_code`, with the tools that reach the person's app and devices beside them, and runs the agent's scripts, answering their calls. A Deno waits for the next script, started while the agent reads the last answer, so a script starts in milliseconds.
- [`mcp_main.calx`](mcp_main.calx): `loom mcp` as a program of its own, which the desktop app ships beside itself and gives its agents, because it starts in less than half the time of the whole app.
- [`brains.calx`](brains.calx): a backup brain (PLAN.md, "A backup brain"): which program an agent's turn moves to when its own runs out of usage or doesn't start, telling a usage or rate limit from other errors, the one line the reply shows, and loom's summary of a chat that moves to another program, made from the chat itself.
- [`codemode.calx`](codemode.calx): Code Mode's pieces: the catalog of tools a script can call, their TypeScript signatures from their JSON Schemas, the search, the waiting Deno with no permissions that runs each script from a `data:` URL, and the pinned Deno release the instance fetches.
- [`mcpclient.calx`](mcpclient.calx): `loom mcp` as the client of an agent's MCP servers and its person's plugins' tool servers in Code Mode, over stdio or Streamable HTTP.
- [`icons.calx`](icons.calx): an MCP server's own icons for its badge: the best of what its `serverInfo.icons` gives, for a light background and a dark, fetched with a cap on their size and time, by the test of a server and by `loom mcp`. The instance checks each is a picture and keeps it small (`files.icon_png`).
- [`links.calx`](links.calx): links in the chat (PLAN.md, "Links and sources"): the addresses in a message, the Sources list taken off the end of an agent's reply, and each page's title and its site's icon, looked up on a thread of its own, only over https and never on the person's own network, with its preview picture (`og:image`) too for a link pasted in the composer (`link.preview`, PLAN.md "Links in the composer"). The instance keeps a page's and a site's for as long as it runs, and gives each message `links` as they come, with `message.updated`.
- [`instance.calx`](instance.calx): one loop on std.http.server, listening on 127.0.0.1. It serves the HTTP routes and the `/ws` WebSocket from [protocol.md](../protocol/protocol.md), and runs each agent's turns through ACP, turning what the agents say into events and deltas.
- [`store.calx`](store.calx): SQLite. Every row is kept per person, and that includes the event log. What only the instance should read (secrets, ACP programs' settings, webhook secrets) is sealed under `secret.key`, beside the database. It keeps the recordings of tasks the person taught and what agents propose until the person keeps or drops it.
- [`hashing.calx`](hashing.calx): argon2id hashing on a thread of its own, so a login doesn't hold up the loop.
- [`acp.calx`](acp.calx): the ACP client. Each agent program runs as a process of its own, written to and read by a thread of its own, in a process group of its own so stopping it stops what it started; the instance hears when it has stopped.
- [`browser.calx`](browser.calx): the agent's browser (PLAN.md, "The agent's browser"). A headless Chrome, Edge or Chromium for each agent that uses one, with its profile in the instance's data, driven over the DevTools protocol (std.http.websocket) by a thread of its own. It gives the page as an outline of its accessibility tree, with refs to click and type into, draws `html_preview`'s page in a tab of its own with what its console said, records what the person does while they have it as steps for teaching a task (`browser.record`), names the site each page is on so the instance adds that site's notes and the names of the secrets kept for it, says when a page wants a password or a code, types secrets into fields without the agent seeing them, and opens the page it was on again when it starts after a close. The instance closes it when the agent's turn ends and no one watches it, and after 5 idle minutes. It also names what a Linux server lacks for it (a browser, fonts), which `loom install` installs (setup.calx). On Windows it finds Edge where the registry's App Paths say, when it isn't in the usual folders.
- [`chrome.calx`](chrome.calx): the browser and fonts a Linux server without them fetches for itself, as the loom user: Chrome for Testing's headless shell and Noto fonts, into `browser/` in the instance's data, with a fontconfig file for the fonts, and the libraries the browser lacks, from ldd. A Mac without Chrome or Edge fetches the headless shell too, the build pinned here with its SHA-256, refused if the download isn't that file.
- [`backup.calx`](backup.calx): `loom export` and `loom import` (PLAN.md, "Moving an instance"). An instance's data folder goes into one `.tar.zst`, a file at a time: the database as a consistent snapshot (`VACUUM INTO`, safe while it runs), `secret.key`, and the folders, but not `acp/` (ACP programs for one machine) or `plugins/` (written again). Import makes a new instance in an empty folder and says which ACP agents to install again. `loom serve --backups DIR` writes one there each day, on a thread of its own, and keeps the newest 7 (`--backups-keep`).
- [`move.calx`](move.calx): moving an instance (PLAN.md, "Moving an instance"). `loom receive` prints a one-time move code and takes the move; `instance.move` sends the export there in chunks on a thread of its own. Each chunk is sealed with XChaCha20-Poly1305 under a key from the code, which also gives the bearer token, and the last request says how many there were, so none can be left out or reordered.
- [`noise.calx`](noise.calx): the network side of an instance in the desktop app, once the owner turns phones on (`instance.phones`). A bridge on a thread of its own listens on every address, on port 47420 if it can, and takes only `/ws/noise`: the Noise NK handshake against the instance's X25519 key, then each phone's frames to its own `/ws` on loopback and its HTTP requests to the instance's routes, both ways sealed, marked `X-Loom-Bridge: noise` so the instance knows they came from a phone (and a script token is no use through it). Anything else there gets `noise_only`.
- [`announce.calx`](announce.calx): while phones are on, the instance says where it is on the local network with mDNS: `_loom._tcp` on its Noise port, with its Noise key as the TXT property `key`, so a phone finds the PC again when its address changes.
- [`sandbox.calx`](sandbox.calx): sandboxes for the agents of everyone but the owner, and for any agent marked isolated (PLAN.md, "Sandboxes"), with `loom serve --sandboxes podman` (or `docker`): a rootless Podman container each, which sees only the person's folder and the downloaded agent programs, and runs their agent programs with `podman exec`, and for an agent closed to the network, one of its own with `--network none`. Files the instance writes in the person's folder, or reads from their agent's links, go through it. A release's sandboxes come from its own version's image, and the ones an older loom's image made are found by the image's id when the instance starts, and made again from the new one once nothing runs in them. It refuses to run on Windows, where a sandbox can't see the instance's folders at the same paths.
- [`egress.calx`](egress.calx): the way out of a sandbox closed to the network: `loom egress` in it, which carries each connection made to 127.0.0.1:3128 there over `exec`'s standard input and output, and the instance's end, which passes loom's tools on to the gate and is a proxy that lets out only the hosts on the agent's list, never the server itself or a network of its own. The agent's browser goes through it too.
- [`gate.calx`](gate.calx): the sandboxes' one way to the instance, a listener on 127.0.0.1 that pasta lets them reach (and a closed sandbox's egress). It passes `loom mcp`'s routes on, and nothing else.
- [`stage.calx`](stage.calx): taking OpenBot's data out of the folder of the user it runs as, for `loom import openbot --from-user` and `loom install --import`: its database and shared tables as snapshots from VACUUM INTO on a read-only connection, safe while OpenBot writes, each agent's instructions, the skills, the chats' files but not ones that look like secrets, its Claude provider for `carry_provider`, and the folders in the user's home that the agents name by path (the git repo each is in), into a staged folder in the instance's `imports/`. What waits for the instance is `imports/pending.json`, which it takes once a second when it has an owner, running `import.run` for them and writing what came to `imports/done.json`.
- [`installer.calx`](installer.calx): ACP agents from the ACP Registry, on a thread of its own: reading the registry, downloading, checking and unpacking an agent, and installing the npm agents the desktop app finds, pinned to the registry's version, so they start with node rather than npx. `serve --registry` points it at a mirror.
- [`commands.calx`](commands.calx): what an agent may do with loom's commands through `run_command` (PLAN.md, "Agents can do anything the app can"): which run at once, which ask the person first, and which are the person's alone, and the list `list_commands` gives.
- [`plugins.calx`](plugins.calx): plugins (PLAN.md, "Plugins"): reading a plugin's `plugin.toml` and checking its files, what it asks for (`tools`, `agents`, `cmd:<name>`), and what of that waits for its person's yes. The instance keeps plugins with a revision for each change, a panel's data (1 MB at most), and runs an allowed plugin's tool server for every agent, from a folder of its files.
- [`routines.calx`](routines.calx): when a routine runs, from its schedule: chosen days at several times, every few hours within a window of the day, or every N minutes, in its time zone through std.time's `TimeZone`; its next three runs, and its times in a week for the calendar. The instance looks for routines that are due once a second, and runs them as a quiet turn of their agent's, which the person sees only through what the agent posts with `routine_post` (PLAN.md, "Routines"); here too are what the agent is told of that, how a run ended, why a time was skipped and what to do about it, and OpenBot's names for the routine tools. A run due while a turn goes on in its chat waits for it, up to 10 minutes. `POST /hooks/<id>` runs one from outside, with its secret. `serve --test-minute-ms` shortens the minute, for tests.
- [`learn.calx`](learn.calx): what an agent learns from a chat (PLAN.md, "Memory"): whether its permission mode keeps a note or a fix on its own, what it's told when its chat has paused (4 minutes after the person's last turn, which the instance watches for from the same once-a-second look as routines), a fix's change as the lines it removes and adds (std.diff), and what a reply shows under it. The instance keeps the proposals, runs the quiet turn, and puts in, asks about and undoes each one.
- [`flows.calx`](flows.calx): routine flows (PLAN.md, "Routine flows"): reading a routine's `flow`, which steps go next once the ones they wait for have finished, which are skipped, and what a step is told of its inputs' answers. The instance keeps the flows that are running, runs each step as a quiet turn in its agent's chat, and moves them along from its loop as runs end.
- [`tables.calx`](tables.calx): shared tables (PLAN.md, "Shared tables"): what a table's name and a row's fields may be, a row as `table.write` takes it, a query as `table.rows` takes it, who may change a row, and which rows read as untrusted. The rows are in the store, as JSON, found with `json_extract`; the instance has the `table.*` commands.
- [`rules.calx`](rules.calx): rules on what's touched (PLAN.md, "Rules, records and limits"): a rule as `rule.put` takes it, checked, and in words; what an ACP tool call, a what-if or one of loom's tools touches (its site, paths, command, tool, effect and who started the turn); and matching them, deny first, then ask, then allow, with what can't be read denying. The rules are in the store; the instance has the `rule.*` commands and asks them before each action.
- [`cards.calx`](cards.calx): cards in the chat (PLAN.md, "Cards in the chat"): checks and tidies what an agent gave `show_card`, choices, a form, a checklist, a table, progress or facts, and where it goes (`place_of`: choices and forms at the end), into the card the instance keeps as a `card` block, or says why it can't be one; checks a form's answers (`form_answer`) and keeps them on the card; and loom's own cards: the sign-in, and `browser_ask_secret`'s, with the fields the person fills in and the name each is offered to be kept as, made from the site.
- [`update.calx`](update.calx): updating the server's own program (PLAN.md, "Updates and versions"; protocol.md, "Updating the instance"), for `loom update` and the instance's `instance.update`: the newest release's manifest, checked against the release key, the program for this machine, checked against the manifest's SHA-256, put beside this one as `.new` and swapped in with two renames, the old one kept as `.old`. The instance does the downloading on a thread of its own. It says how the instance runs, which says how it comes back: under systemd it exits with 75 for the unit to start the new program, by hand it starts the new one with the same arguments and port, and in Docker or the desktop app it doesn't update itself. `loom serve --test-release MANIFEST KEY` points it at a test's releases, and is refused without `--test-fast-hashes`.
- [`setup.calx`](setup.calx): `loom install`, run as root on a Linux server: the `loom` user (no shell, no rights beyond `/var/lib/loom`, which only it can read), the program in `/usr/local/bin` for the command line, and a copy of its own for the service in `/var/lib/loom/bin`, which the instance can update (`loom update` as root updates both, and the command line says when the service runs a newer loom than itself, from the version the service answers with), a hardened systemd unit that runs that copy's `loom serve` as `loom`, with `LOOM_SERVICE=systemd` so an update knows systemd starts it again, and Caddy for TLS with `--domain`, or `tailscale serve` without one, unless given `--no-tailscale`. It reads `tailscale serve status --json` first and leaves what's served alone: it takes the HTTPS port already serving loom, or the first of 443, 8443, 10000 and on with nothing at `/` or `/api`, or `--https-port N`, and gives the address it used. Unless given `--no-sandboxes`, it sets up rootless Podman for `loom`, for the sandboxes of everyone but the owner: Podman, pasta and newuidmap (with apt-get), a range of ids in `/etc/subuid` and `/etc/subgid`, and lingering, for a session of its own. The unit then runs `loom serve --sandboxes podman` in that session, and can't forbid new privileges, which newuidmap needs. It starts the service and gives the address and the setup code from its log, as JSON with `--json` (`address`, `setup_code`, `link_code` (a link code for the setup code, for an agent to add the server to its person's app), `version`, `via`, `local`, `data`, `user`, `service`, `import`, `next` and `steps`). `--import openbot[:USER]` stages OpenBot's data from USER (`openbot`) for the owner, who gets it once they set up. A second run brings it up to date, and it leaves alone a unit or a Caddyfile it didn't write.
- [`install.sh`](install.sh): what a fresh server runs, `curl -fsSL https://github.com/aaen-studios/loom/releases/latest/download/install.sh | sudo sh` (`-s -- --domain loom.example.com` for a domain). It only fetches the release's `loom` for the machine, checks its SHA-256 against the manifest, and runs `loom install`. CI runs it on a fresh Ubuntu runner.
- [`push.calx`](push.calx): push to the iPhone app through APNs, on a thread of its own: a provider token signed ES256 with the owner's APNs key, made again every 50 minutes, and an HTTP/2 POST per phone. The instance hands it a notify, a question, or a reply the person isn't there to see, for each phone that isn't connected, and forgets the tokens APNs says are gone (protocol.md, "Push"). `serve --test-apns` points it at a fake APNs, for tests.

Trying it from source, from the repository's root:

```sh
calx server/main.calx acp add claude npx -y @agentclientprotocol/claude-agent-acp
calx server/main.calx serve                       # prints a setup code on the first start
```

Then `POST /api/setup` with the code makes the owner. `echo "a password" | calx server/main.calx user add bob` adds a second account. Everything is kept in `loom-data/` unless `--data` names another folder. [`tests/protocol/phase1.calx`](../tests/protocol/phase1.calx) shows a whole session.

The same code is compiled into the desktop app's library for an instance with no server ([PLAN.md](../PLAN.md#an-instance-in-the-desktop-app)).
