# server

Calx: the instance, and the `loom` program.

- [`main.calx`](main.calx): the `loom` command line: `serve`, `user add`, `user list`, `acp add`, `acp list`, `files limit`, `push key` (the APNs key, kept sealed) and `push off`, `ask`, `routine run`, `approvals` and `approve` (the person's scripts, through the running instance's `/api/scripts/`, with their script token), `status` (which also says the user it runs as and whether push is on), `update`, `mcp` and `version`. `serve` won't run as root or an elevated Administrator unless given `--allow-root`, and the tests pass it, since GitHub's Windows runners are elevated. Every command but `serve` and `mcp` takes `--json`, and answers with one JSON object, or `{"error":{"code","message"}}` and a non-zero exit, so an agent over SSH reads it reliably. `install` sets loom up on a server (below). Later `loom receive`.
- [`mcp.calx`](mcp.calx): `loom mcp`, loom's own tools as an MCP server on standard input and output. The instance gives it to every agent's session, and it hands each call back to the instance. The tools are in [`shared/tools.calx`](../shared/tools.calx). In Code Mode (PLAN.md, "Code Mode") it offers `search_tools` and `run_code` alone, and runs the agent's scripts, answering their calls.
- [`brains.calx`](brains.calx): a backup brain (PLAN.md, "A backup brain"): which program an agent's turn moves to when its own runs out of usage or doesn't start, telling a usage or rate limit from other errors, the one line the reply shows, and loom's summary of a chat that moves to another program, made from the chat itself.
- [`codemode.calx`](codemode.calx): Code Mode's pieces: the catalog of tools a script can call, their TypeScript signatures from their JSON Schemas, the search, the prelude each script runs with, starting Deno with no permissions, and the pinned Deno release the instance fetches.
- [`mcpclient.calx`](mcpclient.calx): `loom mcp` as the client of an agent's MCP servers and its person's plugins' tool servers in Code Mode, over stdio or Streamable HTTP.
- [`instance.calx`](instance.calx): one loop on std.http.server, listening on 127.0.0.1. It serves the HTTP routes and the `/ws` WebSocket from [protocol.md](../protocol/protocol.md), and runs each agent's turns through ACP, turning what the agents say into events and deltas.
- [`store.calx`](store.calx): SQLite. Every row is kept per person, and that includes the event log. What only the instance should read (secrets, ACP programs' settings, webhook secrets) is sealed under `secret.key`, beside the database.
- [`hashing.calx`](hashing.calx): argon2id hashing on a thread of its own, so a login doesn't hold up the loop.
- [`acp.calx`](acp.calx): the ACP client. Each agent program runs as a process of its own, written to and read by a thread of its own.
- [`browser.calx`](browser.calx): the agent's browser (PLAN.md, "The agent's browser"). A headless Chrome, Edge or Chromium for each agent that uses one, with its profile in the instance's data, driven over the DevTools protocol (std.http.websocket) by a thread of its own. It gives the page as an outline of its accessibility tree, with refs to click and type into, draws `html_preview`'s page in a tab of its own with what its console said, and stops after 10 idle minutes.
- [`backup.calx`](backup.calx): `loom export` and `loom import` (PLAN.md, "Moving an instance"). An instance's data folder goes into one `.tar.zst`, a file at a time: the database as a consistent snapshot (`VACUUM INTO`, safe while it runs), `secret.key`, and the folders, but not `acp/` (ACP programs for one machine) or `plugins/` (written again). Import makes a new instance in an empty folder and says which ACP agents to install again. `loom serve --backups DIR` writes one there each day, on a thread of its own, and keeps the newest 7 (`--backups-keep`).
- [`move.calx`](move.calx): moving an instance (PLAN.md, "Moving an instance"). `loom receive` prints a one-time move code and takes the move; `instance.move` sends the export there in chunks on a thread of its own. Each chunk is sealed with XChaCha20-Poly1305 under a key from the code, which also gives the bearer token, and the last request says how many there were, so none can be left out or reordered.
- [`noise.calx`](noise.calx): the network side of an instance in the desktop app, once the owner turns phones on (`instance.phones`). A bridge on a thread of its own listens on every address, on port 47420 if it can, and takes only `/ws/noise`: the Noise NK handshake against the instance's X25519 key, then each phone's frames to its own `/ws` on loopback and its HTTP requests to the instance's routes, both ways sealed, marked `X-Loom-Bridge: noise` so the instance knows they came from a phone (and a script token is no use through it). Anything else there gets `noise_only`.
- [`announce.calx`](announce.calx): while phones are on, the instance says where it is on the local network with mDNS: `_loom._tcp` on its Noise port, with its Noise key as the TXT property `key`, so a phone finds the PC again when its address changes.
- [`sandbox.calx`](sandbox.calx): sandboxes for the agents of everyone but the owner, and for any agent marked isolated (PLAN.md, "Sandboxes"), with `loom serve --sandboxes podman` (or `docker`): a rootless Podman container each, which sees only the person's folder and the downloaded agent programs, and runs their agent programs with `podman exec`, and for an agent closed to the network, one of its own with `--network none`. Files the instance writes in the person's folder, or reads from their agent's links, go through it. It refuses to run on Windows, where a sandbox can't see the instance's folders at the same paths.
- [`egress.calx`](egress.calx): the way out of a sandbox closed to the network: `loom egress` in it, which carries each connection made to 127.0.0.1:3128 there over `exec`'s standard input and output, and the instance's end, which passes loom's tools on to the gate and is a proxy that lets out only the hosts on the agent's list, never the server itself or a network of its own. The agent's browser goes through it too.
- [`gate.calx`](gate.calx): the sandboxes' one way to the instance, a listener on 127.0.0.1 that pasta lets them reach (and a closed sandbox's egress). It passes `loom mcp`'s routes on, and nothing else.
- [`installer.calx`](installer.calx): ACP agents from the ACP Registry, on a thread of its own: reading the registry, and downloading, checking and unpacking an agent. `serve --registry` points it at a mirror.
- [`commands.calx`](commands.calx): what an agent may do with loom's commands through `run_command` (PLAN.md, "Agents can do anything the app can"): which run at once, which ask the person first, and which are the person's alone, and the list `list_commands` gives.
- [`plugins.calx`](plugins.calx): plugins (PLAN.md, "Plugins"): reading a plugin's `plugin.toml` and checking its files, what it asks for (`tools`, `agents`, `cmd:<name>`), and what of that waits for its person's yes. The instance keeps plugins with a revision for each change, a panel's data (1 MB at most), and runs an allowed plugin's tool server for every agent, from a folder of its files.
- [`routines.calx`](routines.calx): when a routine runs next, from its schedule: every N minutes, or daily or on weekdays at a time of day in its time zone, through std.time's `TimeZone`. The instance looks for routines that are due once a second, and runs them as a prompt to their agent (PLAN.md, "Routines"). `POST /hooks/<id>` runs one from outside, with its secret. `serve --test-minute-ms` shortens the minute, for tests.
- [`flows.calx`](flows.calx): routine flows (PLAN.md, "Routine flows"): reading a routine's `flow`, which steps go next once the ones they wait for have finished, which are skipped, and what a step is told of its inputs' answers. The instance keeps the flows that are running, posts each step in its agent's chat, and moves them along from its loop as runs end.
- [`tables.calx`](tables.calx): shared tables (PLAN.md, "Shared tables"): what a table's name and a row's fields may be, a row as `table.write` takes it, a query as `table.rows` takes it, who may change a row, and which rows read as untrusted. The rows are in the store, as JSON, found with `json_extract`; the instance has the `table.*` commands.
- [`rules.calx`](rules.calx): rules on what's touched (PLAN.md, "Rules, records and limits"): a rule as `rule.put` takes it, checked, and in words; what an ACP tool call, a what-if or one of loom's tools touches (its site, paths, command, tool, effect and who started the turn); and matching them, deny first, then ask, then allow, with what can't be read denying. The rules are in the store; the instance has the `rule.*` commands and asks them before each action.
- [`cards.calx`](cards.calx): cards in the chat (PLAN.md, "Cards in the chat"): checks and tidies what an agent gave `show_card`, choices, a checklist, a table, progress or facts, into the card the instance keeps as a `card` block, or says why it can't be one.
- [`setup.calx`](setup.calx): `loom install`, run as root on a Linux server: the `loom` user (no shell, no rights beyond `/var/lib/loom`, which only it can read), the program in `/usr/local/bin`, a hardened systemd unit that runs `loom serve` as `loom`, and Caddy for TLS with `--domain`, or `tailscale serve` without one. Unless given `--no-sandboxes`, it sets up rootless Podman for `loom`, for the sandboxes of everyone but the owner: Podman, pasta and newuidmap (with apt-get), a range of ids in `/etc/subuid` and `/etc/subgid`, and lingering, for a session of its own. The unit then runs `loom serve --sandboxes podman` in that session, and can't forbid new privileges, which newuidmap needs. It starts the service and gives the address and the setup code from its log. A second run brings it up to date, and it leaves alone a unit or a Caddyfile it didn't write.
- [`install.sh`](install.sh): what a fresh server runs, `curl -fsSL https://github.com/aaen-studios/loom/releases/latest/download/install.sh | sudo sh` (`-s -- --domain loom.example.com` for a domain). It only fetches the release's `loom` for the machine, checks its SHA-256 against the manifest, and runs `loom install`. CI runs it on a fresh Ubuntu runner.
- [`push.calx`](push.calx): push to the iPhone app through APNs, on a thread of its own: a provider token signed ES256 with the owner's APNs key, made again every 50 minutes, and an HTTP/2 POST per phone. The instance hands it a notify, a question, or a reply the person isn't there to see, for each phone that isn't connected, and forgets the tokens APNs says are gone (protocol.md, "Push"). `serve --test-apns` points it at a fake APNs, for tests.

Trying it from source, from the repository's root:

```sh
calx server/main.calx acp add claude npx -y @agentclientprotocol/claude-agent-acp
calx server/main.calx serve                       # prints a setup code on the first start
```

Then `POST /api/setup` with the code makes the owner. `echo "a password" | calx server/main.calx user add bob` adds a second account. Everything is kept in `loom-data/` unless `--data` names another folder. [`tests/protocol/phase1.calx`](../tests/protocol/phase1.calx) shows a whole session.

The same code is compiled into the desktop app's library for an instance with no server ([PLAN.md](../PLAN.md#an-instance-in-the-desktop-app)).
